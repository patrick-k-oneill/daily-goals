# The cloud pad is iCloud Drive files behind a local module, split by year, pulled before pushed

Every device keeps the pad in the hidden root of the app's iCloud container, under `pad/` (#6): each feature's index — templates, tombstones and declined suggestions for goals, tombstones for gratitude — and one file of entries per year (`entries-<year>.json`, the year a period key or reflection date starts with), so a check tap rewrites one year's file rather than the whole history, the remedy ADR 0004 names. File text is canonical, items sorted by key and object keys sorted, so two devices holding the same pad write the same bytes and see nothing to push. Each file carries a schema version: an older app leaves a newer file alone, and a damaged file is merged from nothing and never overwritten. The engine pulls — reads every file and merges each part in through the feature merges (ADR 0005) — when the pad opens, returns to the foreground, hears another device write, or iCloud comes back; it pushes only the files whose text the cloud lacks, two seconds after the last local write, and never before it has read the cloud once, so a fresh device restores the pad instead of writing its seed over it. The device side is a local Expo module (`modules/icloud-pad`, Swift) doing the three things Apple requires of iCloud Drive documents on iOS and nothing else: a metadata query, the only way a device learns what other devices wrote, which doubles as the change signal; downloading on demand, since iOS never downloads unasked; and file coordination on every read and write. The versions iCloud keeps when two devices write one file at once are read like any other device's copy and merged in, so it doesn't matter which one iCloud kept. iCloud Drive documents have no development or production environment — the container is one directory on the device whatever signed the build (and `expo-document-picker`'s config plugin strips that entitlement anyway) — so a development client on the iPad and a TestFlight build on the phone share one pad.

Rejected: `react-native-cloud-storage`, which #6 named — it reads and writes the container with plain file calls and does none of the three, and its open issue #82 reports exactly the resulting failure, each device seeing only its own files; the iCloud key-value store as a change signal, unnecessary once the metadata query delivers updates; CloudKit records, the most work, for a latency problem that hasn't appeared; and adopting the cloud pad wholesale on a fresh device, redundant since deterministic ids and epoch stamps already make the seed lose every merge. Web has no iCloud: the pad file (#4) stays its bridge.

Revisited 2026-11-13 for the removal of upcoming events (#95) and for carryover suggestions (#58): the layout version is 3. It has no events file: an `events.json` an earlier build wrote is outside the layout, so it is neither read nor written and stays where it is. The goals index now holds `declinedSuggestions`, sorted and left out when there are none, so a suggestion declined on one device stays declined on the others. That field is why the version moved: a build on layout 2 would read the index, merge it without the field and write it back without it, and the two builds would overwrite each other's index without end; a newer version makes the older build leave the file alone until it is updated. A template's first retirement (ADR 0008) needs no place of its own, since it is the `retiredAt` the index already carries, and neither does an entry's `carriedFrom`, which travels with the entry in its year's file.
