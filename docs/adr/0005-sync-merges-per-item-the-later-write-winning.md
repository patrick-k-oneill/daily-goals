# Sync merges the pad per item, the later write winning, with tombstones for removals

Every device holds a full copy of the pad and reconciles by merging, never by overwriting (#6). Each template and entry carries `updatedAt`, and a gratitude entry its `writtenAt`: the stamp of the last write, from the writing device's clock. Merging is per item, keyed by id (templates, entries) or reflection date (gratitude): the later stamp wins whole; a tie goes to a canonical comparison of the content so every device picks the same copy; and the result is sorted by key, so a merge is the same whichever side is local and a device with nothing new has nothing to push. A removal leaves a tombstone, the key and when: a tombstone at or after an item's stamp removes it, and an item written after its tombstone revives it and spends the tombstone. Identity is deterministic so that two devices writing the same morning produce one line: a materialized entry's id is `<templateId>:<periodKey>`, a seed template's is `seed:<cadence>:<sortOrder>`, a line nobody has written on is stamped the epoch (so any real write beats an untouched copy), and materialization skips tombstoned ids. Retiring a template records `retiredAt` and `retiredOn`, the day that moment fell on where it was made; an untouched line on a period after the one holding that day is a ghost a stale device wrote before it heard, and every device drops it the same way, no tombstone needed. Data from before stamps (goals store v2, pad file schema 1; gratitude v1 already carried `writtenAt`) is stamped legacy, one millisecond after the epoch, with retirements at the epoch and seed and materialized ids rewritten: an upgraded pad wins over a fresh device's seed and loses to any real write, so the last device to upgrade cannot undo what the others wrote before it (#69). Two legacy copies of a line tie and fall to the content comparison; with no history there is nothing better to do.

Rejected: per-check merging, which needs a stamp per check and would roughly double the goals store (ADR 0004) — so the same line tapped on two offline devices keeps only the later device's marks, a known limitation whose upgrade path is a three-way merge against a stored base; replace-on-conflict, which is a merge that drops data, the failing test; and stamping legacy data the moment it arrived on a device, the first choice here (#69): it beat the seed, but also every real write made before that device upgraded, so the last device to upgrade won every shared line. Concurrent writes to the cloud converge without coordination: whichever copy iCloud keeps, each device pulls it, merges, and pushes only if its pad differs from the last cloud content it saw, so two rounds settle it.

Revisited 2026-11-24 for the ghost rule's time zone (#105): the retirement's period was read from `retiredAt` on each device's own calendar, so two devices in different zones could disagree about one line and rewrite a year's file at each other without end. The template now carries `retiredOn`, written with the retirement from the retiring device's today, and the ghost rule reads only that. A retirement from before the day was recorded takes one at its next merge, read off that device's calendar; where two copies of the same retirement carry different days the earlier stands, so every device settles on one. Rejected: reading the day off the stamp in UTC, which is the same everywhere but wrong in the evening west of UTC, where the stamp is already on the next day and the line a stale device writes that next morning would stay.

Revisited 2026-11-24 for the check count (#101): a line showed a check nobody added. The later stamp wins a row whole, so a check tap or a rename made on a device that had not heard a goal's count was changed carried the old count along and won; so did the line such a device wrote for a new day from its old template, when it was the only copy. The count now carries a stamp of its own, `countAt`, on the template and on the line: set by an edit that changes the count, taken from the template by each line it writes, and absent while a count stands as first written. A merge still gives the row to the later write and then gives it the count set last, with the marks and labels of the later write fitted to it, so a tap and a count change made apart both stand. Writing today's page gives a line already there its template's count when that was set after the line's own, which is what the device would have written had it heard; a past page stays as written. A row from before the field (store v4, pad file 2 to 6, cloud layout 3 and earlier) has its count credited to its last write when it is read, the latest the count can have been set: it stands against a copy written earlier and yields to any count set since, and a legacy row's count is stamped legacy with the rest of it. Rejected: giving a line its template's count at every merge, which mends the stale line and leaves the stale template, the rename case, winning its row with the old count.
